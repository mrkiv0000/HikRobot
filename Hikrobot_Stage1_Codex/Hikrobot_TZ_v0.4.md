# Техническое задание: приём данных камер Hikrobot в Python

Версия: 0.4 — основная программа Python, уточнённые требования. Дата: 01.10.2026.

## 1. Назначение

Разработать программу на Python, которая принимает данные от камер Hikrobot MV-ID6120PM-00C-NNG, извлекает информацию о QR-кодах, хранит последние результаты и предоставляет ПЛК Siemens готовые данные по TCP-запросу.

Обмен с камерами, парсинг и определение стороны детали переносятся из ПЛК в Python. ПЛК получает только ID детали и номер стороны SN.

Исходные материалы: TechVision.scl — источник правил парсинга и определения стороны; main.py — рабочий фрагмент приёма данных одной камеры. Из TechVision.scl используются правила парсинга и определения стороны. Объединение результатов камер и проверка количества кодов реализуются по разделу 8 этого ТЗ; существующий каскад ПЛК не переносится автоматически.

## 2. Камеры и запуск съёмки

- Поддерживается от 1 до 4 камер в общей сети.
- Каждая камера работает как TCP-сервер; порт по умолчанию — 2002, с возможностью изменения.
- Python работает как TCP-клиент камер и принимает данные одновременно по независимым соединениям.
- Камеры запускают съёмку от внешних датчиков. Ни Python, ни ПЛК не отправляют камерам команды запуска съёмки.
- В каждой камере параметр Number of 2D Code устанавливается равным 4: это максимальное количество распознаваемых 2D-кодов, а не обязательное количество перед отправкой результата.
- Настройка в программе задаёт ожидаемое суммарное количество кодов для текущего техпроцесса и сама по себе не изменяет конфигурацию камер.
- Программа не получает состояние внешних датчиков ни напрямую, ни через ПЛК или дискретные выходы камер. Границы сбора определяются по сообщениям камер и времени.
- Камеры должны отправлять распознанные коды во время активного триггера. Для отсутствия чтения используется сообщение NoRead после завершения триггера; фактическую выдачу такого сообщения необходимо проверить при наладке каждой камеры.

## 3. Пользовательский интерфейс и настройки

Предусмотреть вкладку «Настройки» со следующими параметрами:

| Параметр | Требование |
|---|---|
| Количество камер | От 1 до 4 |
| Ожидаемое количество QR-кодов | Суммарно для текущего техпроцесса по всем выбранным камерам; целое от 1 до 4 |
| Время сбора результатов | Настраиваемое положительное время от первого кода; начальное значение для проверки — 3 с |
| IP-адрес | Отдельно для каждой камеры |
| TCP-порт | Отдельно для каждой камеры; по умолчанию 2002 |
| Подключение | Одна кнопка «Подключить все камеры» для камер, заданных полем «Количество камер» |
| Сохранение | Кнопка «Сохранить настройки» |
| Состояние камеры | «Подключено», «Подключается», «Отключено» отдельно для каждой камеры |

Маска подсети и шлюз в интерфейсе отсутствуют. Программа не изменяет сетевые настройки камер или компьютера.

TCP-порт задаётся отдельно для каждой камеры, по умолчанию 2002. Одинаковый номер порта допустим у всех камер с разными IP-адресами: для каждой пары IP/порт создаётся независимое соединение. Отдельные поля позволяют подключить камеру с другим настроенным портом.

Кнопка «Подключить все камеры» запускает подключение всех выбранных камер. Отказ одной камеры не мешает подключению остальных; статус и причина ошибки показываются отдельно для каждой камеры. До проверки полной готовности всех выбранных камер нельзя выдавать успешный результат техпроцесса.

Настройки записываются на диск только по кнопке «Сохранить настройки» и автоматически загружаются при следующем запуске. Само подключение не сохраняет изменения. Перед сохранением проверяются значения полей. При подключении используются значения, отображаемые в интерфейсе; несохранённые изменения обозначаются явно. Изменение количества камер, ожидаемого количества кодов и времени сбора применяется между циклами, а не к уже открытому сбору.

При первом запуске без сохранённой конфигурации IP-адреса заполнены значением 0.0.0.0, порты — 2002. 0.0.0.0 служит заполнителем и не допускается как адрес удалённой камеры при подключении. Начальные значения количества камер и ожидаемых кодов — 1; время сбора — 3 с. Автоматическое подключение при запуске не требуется.

На основном экране отображаются последние распарсенные записи, текущая структура для ПЛК, состояние сбора, полученное/ожидаемое количество кодов, оставшееся время и ошибки. Технология интерфейса выбирается на этапе реализации.

## 4. Приём и парсинг

Формат сообщений сохраняется:

```text
{id:999999999999999,p:(9999,9999),a:999;id:...}
```

Фигурные скобки ограничивают сообщение; точка с запятой разделяет записи QR-кодов. Для каждой записи извлекаются:

| Поле | Значение | Представление |
|---|---|---|
| ID | Код детали | Строка длиной до 15 символов, совместимая с String[15] ПЛК |
| X | Первая координата в p:(X,Y) | Число, соответствует Real в SCL |
| Y | Вторая координата в p:(X,Y) | Число, соответствует Real в SCL |
| A | Угол из поля a | Число, соответствует Real в SCL |
| SN | Номер стороны, вычисленный из A | Целое 1–4 |

ID хранится как строка: ведущие нули сохраняются. При корректном входном сообщении результаты должны соответствовать парсеру SCL. Координаты не меняются местами; масштабирование и преобразование координат не вводятся. X и Y принимаются как дополнительные данные и отображаются в истории; в текущем этапе они не участвуют в подсчёте кодов, определении стороны или формировании строки для ПЛК. Камера передаёт A, а SN вычисляется только в Python и не ожидается во входном сообщении.

Для каждой камеры используется отдельный буфер приёма. Программа должна корректно обрабатывать одно сообщение, пришедшее несколькими TCP-чтениями, и несколько сообщений, пришедших одним чтением. Неполное сообщение ожидает продолжения.

Сообщение NoRead (включая согласованный вариант {NoRead}) означает: цикл съёмки соответствующей камеры завершился без распознанного кода. NoRead фиксируется отдельно для каждой камеры как результат отсутствия чтения, но само по себе не является ошибкой детали при работе нескольких камер. Оно не увеличивает число кодов, не добавляется в историю распарсенных QR-кодов и не стирает результаты других камер.

Результат оценивается суммарно по всем выбранным камерам в одном проверяемом цикле:

- Если есть коды, проверяется количество уникальных ID относительно ожидаемого. NoRead других камер не влияет на проверку количества и не блокирует успех.
- Если кодов нет и от всех выбранных камер пришёл NoRead, выдаётся ошибка «Код не прочитан».
- При одной выбранной камере её NoRead без прочитанных кодов вызывает ошибку «Код не прочитан».
- Молчание камеры или разрыв соединения не считается NoRead. При отсутствии ответа одной камеры нельзя утверждать, что все камеры завершили цикл без чтения.

NoRead не сообщает момент начала съёмки. Таймер сбора запускается от первого кода, как описано в разделе 8; NoRead без кодов обрабатывается путём накопления результатов камер для отдельного проверяемого цикла.

Пустые TCP-чтения, неполные сообщения и повреждённые данные не считаются NoRead. Нулевое чтение сокета означает закрытие соединения; неполные сообщения ожидают продолжения; повреждённые данные отмечаются как ошибка формата и не используются как успешные результаты. Проверки формата не должны воспроизводить случайные ошибки старого парсера.

## 5. Определение стороны

Сторона определяется в Python по той же логике, что в HikrobotParser. Сначала A преобразуется в целое с семантикой REAL_TO_INT исходного ПЛК; затем применяется таблица:

| Целочисленный угол | SN | Сторона |
|---|---:|---|
| 0–45 или 316–360 | 3 | Лево |
| 46–135 | 1 | Верх |
| 136–225 | 4 | Право |
| 226–315 | 2 | Низ |

Нельзя заменять преобразование простым отбрасыванием дробной части. При реализации необходимо проверить совместимость округления, включая значения на половине шага и границы диапазонов, а также влияние представления Real.

Во всех разделах программы, истории и структуре для ПЛК поле стороны называется SN. SN — номер стороны, а не исходный угол A.

Допустимый исходный угол A — от 0 до 360 включительно. Перед REAL_TO_INT проверяется исходное числовое значение: A < 0 или A > 360 вызывает ошибку «Угол вне диапазона 0–360». Для такого результата SN не вычисляется и подтверждённая строка для ПЛК не формируется. Автоматическая нормализация и ограничение угла границами не выполняются. Некорректный результат сохраняется в диагностике; ошибка угла блокирует подтверждение затронутого цикла. Нечисловое или неконечное значение A относится к ошибке входных данных.

## 6. Хранение последних данных

Предусмотреть массив из 10 записей с полями ID, X, Y, A, SN.

Предлагаемое поведение для первой версии:

- Одна запись соответствует одному распарсенному QR-коду.
- Новые записи добавляются в порядке обработки полных сообщений; внутри сообщения сохраняется порядок кодов.
- После заполнения массива новая запись вытесняет самую старую.
- История сохраняет распарсенные наблюдения, включая повторные ID. Она отделена от набора кодов текущего цикла: повторные наблюдения в истории не увеличивают количество кодов при проверке техпроцесса.

При каждом запуске история начинается пустой. История на диск не сохраняется и после перезапуска не восстанавливается; сохранение настроек не сохраняет историю. Массив последних записей не является очередью подтверждённых листов для ПЛК.

## 7. Данные и строка для ПЛК

Основная программа сохраняет проверенный набор записей. Каждая запись содержит поля ID и SN:

| Поле | Значение |
|---|---|
| ID | Код детали, строка до 15 символов; ведущие нули сохраняются |
| SN | Номер стороны: 1 — верх, 2 — низ, 3 — лево, 4 — право |

Согласованный формат одной строки:

```text
ID;SN\r\n
```

Пример:

```text
531952002000010;3\r\n
```

В примерах обозначение `\r\n` означает два фактических символа конца строки: CR (0x0D) и LF (0x0A), а не четыре печатных символа. Разделитель полей — точка с запятой. Кодировка строки — ASCII. X, Y, A и история из 10 записей в эту строку не включаются.

ID и SN берутся из одной записи. Программа формирует и отображает строку как подтверждённый результат только после окончания полного окна сбора и успешной проверки цикла. Промежуточные данные можно показывать отдельно, но нельзя обозначать подтверждёнными. При начале нового цикла или его ошибке предыдущая строка не должна считаться актуальным результатом текущей детали; результат имеет отдельный внутренний признак актуальности.

Формат запроса ПЛК пока не определён. На текущем этапе требуется сформировать строку внутри программы и отобразить её в интерфейсе. Реализация обмена по запросу ПЛК выполняется после согласования команды запроса, адреса и порта сервера Python, поведения при отсутствии актуального результата и подтверждения получения. Предлагаемая роль Python при будущем обмене — TCP-сервер, ПЛК — TCP-клиент.

При нескольких разных ID в успешном цикле сохраняется весь набор результатов. Для каждой уникальной записи формируется и отображается отдельная строка ID;SN с CR/LF в порядке первого получения ID. При одном ID отображается одна строка. Это внутреннее представление и отображение набора, а не утверждённый порядок передачи ПЛК. Команда запроса, выбор записи для ответа и порядок передачи нескольких строк будут определены на последних этапах вместе с протоколом ПЛК; в текущую реализацию TCP-обмена они не входят.

## 8. Сбор и объединение результатов камер

Проверка количества кодов входит в требования к программе. Ожидаемое количество задаётся для всей детали по всем выбранным камерам, а не отдельно для каждой камеры.

### 8.1. Окно сбора

1. В состоянии ожидания первый корректный распознанный код от любой выбранной камеры открывает общий цикл сбора. Сохраняются время начала, ожидаемое количество кодов и длительность окна для этого цикла.
2. От первого кода запускается фиксированный таймер сбора. Начальное значение для наладки — 3 с; длительность настраивается под техпроцесс.
3. Все корректные коды обеих или других выбранных камер, поступившие в пределах окна, добавляются в набор текущего цикла. Учитываются все записи каждого сообщения.
4. Новые сообщения и повторные чтения не перезапускают и не продлевают таймер.
5. Достижение ожидаемого количества не завершает цикл и не означает успех. Отображается промежуточное состояние, например «Получено 1 из 1, проверка продолжается».
6. Если обнаружено больше кодов, чем ожидается, сразу отображается ошибка лишнего кода, но сбор продолжается до конца окна для регистрации всех найденных результатов. Ошибка не снимается последующими пакетами этого цикла.
7. По окончании окна фиксируется набор результатов и выполняется окончательная проверка суммарного количества кодов и состояния связи. NoRead отдельных камер не блокирует успех при нужном количестве уникальных ID. Успех по кодам возможен только после окончания всего окна.
8. При разрыве связи с выбранной камерой во время сбора цикл не может завершиться успешно, даже если ожидаемое количество уже набрано.
9. После фиксации итога программа автоматически возвращается в ожидание первого кода следующего цикла. Дополнительная выдержка времени и обязательное действие оператора «Новый цикл» не требуются. Следующий полученный код открывает новое окно; одинаковый ID допустим в разных циклах.

### 8.2. Правило подсчёта и повторов

Базовое правило из исходного ТЗ: одинаковые ID в пределах одного цикла объединяются, в том числе при чтении разными камерами. Считается количество уникальных ID, а не количество TCP-сообщений или наблюдений. Для диагностики сохраняется источник каждого наблюдения — номер камеры.

В текущей версии считается количество уникальных ID: одинаковый ID от двух камер сохраняется как один код. Две физические этикетки с одинаковым ID по этому правилу также считаются одним уникальным кодом; подсчёт физических этикеток по положению не входит в текущий этап. В набор текущего цикла сохраняется первый корректный полученный результат данного ID, включая X, Y, A и вычисленный из A номер SN. Последующие результаты с тем же ID от любой камеры игнорируются при объединении: первый результат не перезаписывается, счётчик не увеличивается. Различия A или SN у повторных корректных чтений сами по себе не вызывают ошибку. Наблюдения могут оставаться в журнале и истории, но подтверждённая запись берётся из первого результата. При нескольких записях в одном сообщении первым считается результат по порядку записей; между камерами — по порядку обработки полных сообщений в программе.

### 8.3. Итоговая проверка количества

| Ожидается | Получено уникальных кодов за всё окно | Итог проверки количества |
|---:|---:|---|
| 2 | 1 | Ошибка: «Получен 1 из 2 — недостаточно кодов» |
| 2 | 2 | Количество соответствует: «Получено 2 из 2» |
| 1 | 1 | Количество соответствует: «Получено 1 из 1» |
| 1 | 2 | Ошибка: «Получено 2 из 1 — лишний код» |

Общее правило: меньше ожидаемого — недостаточно кодов; равно — количество соответствует; больше — лишние коды. Соответствие количества даёт общий успех при отсутствии ошибок связи, ошибок угла и иных ошибок, препятствующих корректной проверке. NoRead одной или нескольких камер при наличии нужного суммарного набора кодов блокирующей ошибкой не является.

### 8.4. Обязательные сценарии

**Ситуация 1: ожидаются два кода.** Первая камера присылает первый код и открывает окно. Ошибка недостаточного количества сразу не выдаётся. Если второй отличный ID приходит от любой камеры до окончания окна, по окончании окна количество соответствует. Если остаётся один ID, по окончании окна выдаётся ошибка «Получен 1 из 2 — недостаточно кодов».

**Ситуация 2: ожидается один код, на детали есть лишний код.** Первый код открывает окно; состояние «Получено 1 из 1» остаётся промежуточным. Второй отличный ID, поступивший до конца окна, добавляется в набор и вызывает ошибку «Получено 2 из 1 — лишний код». Первый код не должен приводить к преждевременному успеху или выдаче подтверждённых данных ПЛК.

### 8.5. Суммарные результаты и NoRead

Ниже приведены результаты одного проверяемого цикла для двух выбранных камер. A и B обозначают разные ID; A и A — одинаковый ID. Ожидается один уникальный код.

| Результаты камер | Итог |
|---|---|
| Код A + NoRead | Успех после конца окна: один уникальный ID |
| Код A + код A | Успех после конца окна: один уникальный ID |
| Код A + код B | Ошибка: «Ожидаем 1 код, а получили 2» |
| Два разных кода + NoRead | Ошибка: «Ожидаем 1 код, а получили 2» |
| NoRead + NoRead, кодов нет | Ошибка: «Код не прочитан» |
| NoRead одной камеры, вторая молчит | Недостаточно данных для вывода «Код не прочитан» от всех камер |

При ожидаемом количестве 2 сочетание «один код + NoRead» даёт ошибку недостаточного количества по окончании окна. Причина ошибки — суммарное количество кодов, а не сам факт NoRead.

Если кодов нет, NoRead накапливается по номерам выбранных камер. Повторный NoRead одной камеры не заменяет ответ другой. После получения NoRead от всех выбранных камер фиксируется один итог «Код не прочитан», отметки NoRead очищаются и программа возвращается в ожидание новых сообщений. Если до этого поступает код, запускается полное окно сбора от первого кода, а итог определяется по суммарному набору. После завершения окна отметки NoRead этого цикла также очищаются; NoRead внутри окна не запускает отдельный цикл полного отсутствия чтения.

### 8.6. Границы текущего этапа

Разделение соседних деталей, привязка поздних сообщений и сложная логика с запросами на внешний сервер переносятся на следующий этап, после проверки основной программы. Они не являются предварительным условием разработки текущей версии.

Цикл автоматически начинается при получении первого корректного кода и заканчивается по истечении настроенного времени, по умолчанию 3 с. После фиксации результата программа готова к следующему циклу без дополнительного ожидания. Итог предыдущего цикла сохраняется для отображения, но при открытии нового набора он не обозначается актуальным результатом новой детали. Новый набор кодов и отметки NoRead отделены от предыдущего результата.

Текущий алгоритм проверяется на отдельных циклах, не пересекающихся по времени. Он пока не отличает поздний повтор предыдущей детали от первого кода новой: такой пакет может открыть новый цикл. Постоянный запрет уже встречавшихся ID не вводится. Исправление этого поведения и автоматическая привязка сообщений к физической детали относятся к следующему этапу.

Таймер 3 с отсчитывается от первого распознанного кода, а не от перекрытия датчика. Если ни кодов, ни NoRead не пришло, программа не может отличить отсутствие детали от полностью пропущенного чтения. Если пришёл только NoRead части камер, ошибка полного отсутствия чтения не выдаётся без оставшихся ответов; отдельный контроль времени ожидания таких ответов пока не согласован.

Ограничения фиксируются в документации программы. Автоматическое разделение потока деталей, устранение повторного открытия цикла поздними пакетами и привязка к данным внешнего сервера будут описаны отдельным ТЗ следующего этапа.

## 9. Порядок разработки и проверки

Разработка основной программы выполняется по этапам на основе единого ТЗ. Каждый этап завершается проверкой своих требований и фиксацией рабочей версии в Git. Общее испытание не заменяет проверки отдельных этапов.

| Этап | Реализация | Проверка |
|---|---|---|
| 1 | Независимые подключения 1–4 камер, статусы, журнал сырых сообщений | Подключение доступной реальной камеры, код, NoRead, разрыв и повторное подключение |
| 2 | Парсинг ID/X/Y/A, расчёт SN | Известные сообщения, ведущие нули, границы углов и округление, сообщения частями и несколько сообщений подряд |
| 3 | Полное окно сбора, уникальные ID, суммарная обработка NoRead, итог количества | Ситуации 1 и 2, повторы, одинаковые ID, сочетания кодов и NoRead, изолированные циклы |
| 4 | Настройки, сохранение, история 10 записей, отображение состояния и результата | Сохранение по кнопке, перезапуск, отдельные статусы, заполнение истории |
| 5 | Формирование строки ID;SN с CR/LF | Точное содержимое строки, сохранение ведущих нулей, актуальность после успеха и ошибки |
| 6 | Проверка основной программы в сборе | Доступная реальная камера, сообщения с несколькими кодами, NoRead, потеря связи |

Настройки подключения, необходимые для первого этапа, реализуются сразу; четвёртый этап завершает и проверяет весь пользовательский интерфейс.

Сейчас доступна одна реальная камера. Это не уменьшает требование поддержки 1–4 независимых подключений. Полноценная проверка нескольких реальных камер откладывается до доступности оборудования; в отчётах следует явно указывать, какие проверки выполнены на реальной камере, а какие проверены программными тестами входных сообщений.

После согласования протокола ПЛК выполняется отдельный этап TCP-обмена. После работоспособности основной части выполняется отдельный этап разделения соседних деталей и взаимодействия с внешним сервером.

## 10. Критерии приёмки основной программы

- Поддерживаются 1–4 независимых соединения; данные разных камер не смешиваются в буферах приёма.
- Одна кнопка подключает все выбранные камеры. Статусы отображаются отдельно; отказ одной камеры не мешает установлению остальных соединений.
- Программа не получает состояние датчиков из периферии и не отправляет камерам команды съёмки.
- Маска подсети и шлюз отсутствуют в настройках. TCP-порт задаётся отдельно для каждой камеры, по умолчанию 2002.
- Настройки сохраняются только по кнопке «Сохранить настройки» и подгружаются после перезапуска.
- Корректные сообщения с одной или несколькими записями дают ожидаемые ID/X/Y/A/SN. Ведущие нули ID сохраняются.
- Фрагментация и объединение сообщений при TCP-приёме не меняют результат парсинга.
- SN вычисляется в Python из A и соответствует SCL, включая округление и граничные значения. X и Y не используются в текущей технологической логике.
- Углы 0 и 360 допустимы. A вне диапазона вызывает «Угол вне диапазона 0–360», не нормализуется и не приводит к подтверждённой строке ПЛК.
- Ожидаемое суммарное количество кодов задаётся целым числом от 1 до 4.
- История содержит не более 10 последних распарсенных записей и отделена от уникального набора текущего цикла. При запуске она пустая; на диск не сохраняется.
- Первый код запускает фиксированное окно. Достижение ожидаемого количества не завершает его досрочно; повторы и новые пакеты не продлевают таймер.
- Ситуация 1: недостаточное количество проверяется по окончании окна; второй отличный ID внутри окна учитывается.
- Ситуация 2: лишний ID внутри окна вызывает ошибку, даже если нужное количество было набрано раньше.
- Одинаковый ID от разных камер считается одним кодом; сохраняется первый результат с его A и SN. Повтор не перезаписывает запись, а различия угла или SN у корректных повторов не вызывают ошибку.
- Код + NoRead при ожидании одного ID даёт успех по окончании окна; два разных ID + NoRead при ожидании одного дают ошибку лишнего кода.
- NoRead всех выбранных камер при отсутствии кодов вызывает «Код не прочитан». NoRead части камер и молчание остальных не подменяются полным NoRead.
- Пустое чтение сокета и ошибки формата не считаются NoRead. Ошибки связи отображаются отдельно.
- После окончания окна следующий код автоматически открывает новый цикл без дополнительной выдержки времени и без обязательного ручного запуска. Повторный ID в новом цикле допустим.
- Для каждой уникальной подтверждённой записи формируется и отображается строка ID;SN с фактическими CR и LF; порядок отображения — порядок первого получения ID. Незавершённый или ошибочный цикл не выдаётся как актуальный подтверждённый результат.
- Не реализуются в текущем этапе автоматическое разделение соседних деталей и запросы к внешнему серверу.
