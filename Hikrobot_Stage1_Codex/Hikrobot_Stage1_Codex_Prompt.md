# Промпт для Codex: этап 1 — подключение камер и приём данных

Выполни только первый этап разработки основной программы Python для камер Hikrobot MV-ID6120PM-00C-NNG. Нужна рабочая версия, которую я смогу запустить на Windows и проверить с одной реальной камерой.

## Исходные материалы и приоритет требований

В папке проекта находятся:

- `Hikrobot_TZ_v0.4.md` — полное ТЗ будущей программы.
- `hikrobot-interface-v2.html` — согласованный макет веб-интерфейса.
- Этот файл — границы и требования текущего этапа.

Прочитай материалы до реализации. Полное ТЗ описывает несколько этапов; сейчас реализуй только перечисленное здесь. Этот промпт уточняет интерфейс и ограничивает объём этапа 1. Не переходи автоматически к следующим этапам.

Если папка содержит существующий проект или AGENTS.md, сначала изучи их. Сохрани полезный существующий код; не удаляй и не переписывай посторонние файлы. Не заменяй исходный макет демонстрационными данными работающего приложения: оставь файл макета как образец.

## 1. Результат этапа

Программа должна:

1. Запускать локальный веб-интерфейс.
2. Позволять задать 1–4 камеры, IP и порт каждой камеры.
3. Подключаться к выбранным камерам одной кнопкой.
4. Независимо показывать состояние каждого соединения.
5. Принимать реальные входящие TCP-данные и показывать их в журнале с временем и номером камеры.
6. Позволять сохранить настройки и загрузить их при следующем запуске.

Сейчас у меня есть только одна реальная камера. Архитектура должна поддерживать четыре независимых подключения, но не заявляй о проверке четырёх реальных камер без оборудования.

## 2. Технологии и запуск

- Python 3.12, FastAPI, Uvicorn.
- TCP-приём через стандартный asyncio; отдельная задача приёма на каждую подключённую камеру.
- Интерфейс — обычные HTML/CSS/JavaScript, без React, сборки Node.js и внешних CDN.
- Все необходимые ресурсы должны работать без интернета после установки Python-зависимостей.
- Интерфейс по умолчанию доступен только локально: `http://127.0.0.1:8000`.
- Запуск Uvicorn одним worker, без reload в инструкции для испытания: нельзя создавать несколько экземпляров менеджера соединений.
- Для обновления статусов и журнала достаточно одного опроса API примерно раз в 500 мс. Не создавай новый опрос при каждом переключении вкладок.
- Используй небольшую понятную структуру проекта: приложение/API, менеджер камер, конфигурация, статические файлы. Не размещай весь проект в одном огромном файле.
- Предоставь `requirements.txt`, README с точными командами PowerShell и `.gitignore`.

Не добавляй Docker, авторизацию, базу данных, внешние сервисы и установщик приложения.

## 3. Согласованный интерфейс

Придерживайся `hikrobot-interface-v2.html`: его расположение блоков, рамки, цвета и визуальная иерархия согласованы. Не придумывай новый дизайн.

### Левая колонка

- Отдельный блок «Подключение камер».
- Карточки камер с номером, адресом, портом и статусом.
- Статусы видны при переключении любой вкладки.
- Одна кнопка «Подключить все камеры».
- При выборе четырёх камер все четыре карточки должны помещаться слева на обычном настольном экране, как в макете. На небольшом экране допускается адаптивное расположение.
- Показывай все четыре позиции; позиции выше выбранного количества отмечай «Не используется». Не устанавливай к ним соединения.
- Для выбранных камер используй состояния «Отключено», «Подключается», «Подключено». Причину ошибки показывай отдельно рядом с соответствующей камерой, а также в журнале.
- Нельзя показывать «Подключено» только потому, что заполнен IP или нажата кнопка. Это состояние появляется после успешного TCP-подключения.

### Вкладки

1. «Текущий процесс» — главный центральный блок текущего цикла и блок строк для ПЛК сохраняются по структуре макета. В этапе 1 показывай «Обработка циклов будет реализована на следующем этапе», пустые значения вместо количества, таймера и результатов. Не показывай демонстрационные ID, успешный цикл или готовые строки ПЛК.
2. «История» — сохраняется отдельная вкладка, но пока пустая: «История распарсенных кодов будет доступна на следующем этапе».
3. «Журнал» — рабочая вкладка этапа 1: входящие данные и события соединений, с временем и источником.
4. «Настройки» — рабочие поля и кнопка «Сохранить настройки».

Главный экран не должен снова объединять статусы, длинную историю и журнал в одну общую таблицу. Не выводи на главном экране поток сырых TCP-данных — он находится на вкладке «Журнал».

Смена вкладки и перезагрузка страницы не должны разрывать соединения с камерами или создавать дополнительные TCP-клиенты. Соединениями управляет сервер Python, а не браузер. Несколько открытых вкладок браузера используют один серверный менеджер.

## 4. Настройки

Реализуй поля:

| Поле | Значение по умолчанию | Проверка |
|---|---|---|
| Количество камер | 1 | Целое 1–4 |
| Ожидаемое количество кодов | 1 | Целое 1–4; пока сохраняется, но не участвует в обработке |
| Окно сбора, с | 3 | Конечное положительное число; пока сохраняется, таймер не запускается |
| IP каждой из четырёх камер | 0.0.0.0 | Корректный IPv4; 0.0.0.0 допустим как заполнитель при сохранении, но не как удалённый адрес при подключении |
| TCP-порт каждой камеры | 2002 | Целое 1–65535 |

Маску подсети и шлюз не добавляй. Для всех камер может использоваться один номер порта, если IP различаются.

- Не подставляй демонстрационные адреса из макета как фактические настройки первого запуска.
- Настройки сохраняются в JSON только по кнопке «Сохранить настройки». Подключение и изменение полей не сохраняют их автоматически.
- При запуске загрузи сохранённую конфигурацию. Автоматически к камерам не подключайся.
- Путь конфигурации определи относительно проекта/приложения, а не текущей папки запуска команды.
- Записывай конфигурацию через временный файл и замену, чтобы прерванная запись не оставила частичный JSON.
- Если конфигурация повреждена, покажи понятную ошибку, загрузи значения по умолчанию и не перезаписывай повреждённый файл без нажатия «Сохранить настройки».
- Показывай отметку «Есть несохранённые изменения». Она исчезает только после успешного сохранения либо возврата полей к сохранённым значениям.
- При нажатии «Подключить все камеры» используй текущие значения формы, включая несохранённые. Уже установленные соединения не меняются от простого редактирования полей или сохранения.
- В карточке подключённой камеры показывай фактический адрес соединения. Если в настройках адрес уже изменён, не выдавай его за адрес действующего соединения.

## 5. TCP-соединения

Камера является TCP-сервером, Python — TCP-клиентом. Съёмка запускается внешним датчиком. Python не отправляет камерам триггеры, команды настройки, запросы результатов или тестовые строки. Не читай датчик через ПЛК или другую периферию.

- Подключай выбранные камеры параллельно, с независимым тайм-аутом подключения около 5 секунд.
- Ошибка одной камеры не мешает подключению остальных.
- Для позиции с 0.0.0.0 не создавай сокет: покажи «IP-адрес не задан». Продолжай подключение других выбранных позиций.
- У каждой камеры свои сокет, задача чтения и состояние. Нельзя смешивать входящие данные разных камер.
- Не блокируй обработчики HTTP ожиданием TCP-данных.
- Отсутствие пакетов само по себе не означает потерю связи: камера может молчать без запуска съёмки.
- Нулевое чтение означает закрытие TCP-соединения, а не NoRead. Обработай также исключения чтения, сохрани причину и измени статус.
- После ошибки подключения/разрыва пользователь может повторно нажать общую кнопку. На этапе 1 автоматическое переподключение не требуется.
- При повторном нажатии здоровое соединение с тем же адресом сохраняй; отключённые выбранные камеры пробуй подключить заново. Изменённые адреса и исключённые из выбранного количества камеры корректно отключай перед применением новой конфигурации подключения.
- Защити запуск подключения от повторных кликов и конкурирующих запросов: не допускай двух задач чтения для одной камеры. Во время запуска попыток кнопку можно временно блокировать.
- При завершении сервера закрой все соединения и корректно заверши задачи чтения. Не оставляй фоновые задачи после повторного подключения.

## 6. Сырые данные и журнал

На этом этапе важно узнать, что камера действительно отправляет. Принимай любые входящие байты, не требуя заранее определённого формата.

В будущем ожидаются строки вида:

```text
{id:531952002000010,p:(1825,1140),a:12}
{NoRead}
```

Но реальная камера может иметь другие настройки вывода. Не фильтруй данные по наличию `id:`, фигурных скобок или NoRead.

Для каждого события журнала показывай:

- Время получения с миллисекундами.
- Источник: «Камера 1» … «Камера 4» либо «Программа».
- Вид: входящие данные, подключение, закрытие, ошибка.
- Для входящих данных — размер в байтах и экранированное представление байтов, например `b'{NoRead}\r\n'`. CR, LF и непечатные байты должны быть различимы, а ведущие нули и разделители сохранены.

Одна запись входящих данных на этапе 1 соответствует одному чтению TCP, а не обязательно одному полному сообщению камеры. Явно подпиши это в журнале и README: TCP может разделить сообщение на несколько чтений или объединить несколько сообщений. Сборку полных сообщений и парсер реализуем на этапе 2. Не теряй и не переставляй полученные части внутри одного соединения.

- Храни журнал только в памяти, например последние 200 событий FIFO. При перезапуске он пустой.
- Ограничь размер одного чтения, например 8192 байт; журнал и выдача состояния не должны неограниченно расти.
- Обновление браузера не должно добавлять повторные события в журнал. В самом журнале одинаковые реальные входящие чтения не удаляй: они полезны для диагностики.
- Отображай содержимое как текст, не вставляй пакеты через innerHTML. Строка камеры не должна исполняться в браузере.
- Сообщения соединений и ошибок также выводи в консоль сервера.

`{NoRead}` сейчас является обычными принятыми данными. Не запускай от него цикл и не показывай технологическую ошибку «Код не прочитан» на этапе 1.

## 7. Что отложено

Сейчас не реализуй:

- Парсинг ID, X, Y, A и вычисление SN.
- Сбор полных сообщений из TCP-потока.
- Таймер цикла, объединение ID и проверку ожидаемого количества.
- Суммарную технологическую обработку NoRead.
- Историю распарсенных кодов.
- Формирование и передачу строк ID;SN ПЛК, TCP-сервер для ПЛК.
- Разделение соседних деталей и запросы на внешний сервер.
- Имитаторы камер и генерацию фиктивных результатов в работающем приложении.

Ожидаемое количество и время сбора сейчас только редактируются и сохраняются. Программа не должна делать вид, что эти функции уже работают.

## 8. Проверки перед передачей

Выполни доступные проверки запуска приложения, API, валидации и записи/чтения конфигурации. Для менеджера соединений проверь существенные случаи: EOF, ошибка отдельной камеры и отсутствие дублирующих задач при повторном подключении. Для таких автоматических проверок допустимы подмены сетевых вызовов в тестах; отдельное приложение-имитатор не создавай.

Не заявляй, что подключение к моей реальной камере проверено, если у тебя нет доступа к ней. Сетевые ошибки испытаний не маскируй демонстрационными данными.

Если есть возможность проверить веб-интерфейс в браузере, проверь четыре карточки камер и все вкладки на ширине 1366 и 1920 пикселей, а также отсутствие наложений при уменьшении ширины. Если такой возможности нет, укажи это в отчёте.

## 9. Инструкция для моего испытания

Добавь в README краткий последовательный сценарий с ожидаемым результатом:

1. Создать окружение, установить зависимости, запустить сервер, открыть страницу.
2. Выбрать одну камеру, ввести реальный IP и порт 2002, сохранить.
3. Нажать «Подключить все камеры»; дождаться фактического статуса «Подключено».
4. Перейти в «Журнал», активировать датчик/кнопку камеры и показать код. Проверить появление реальных данных.
5. Выполнить съёмку без кода и отпустить датчик/кнопку. Посмотреть, отправляет ли камера NoRead и в каком виде. Если ничего не пришло, записать это как результат проверки, а не как автоматически установленную ошибку программы.
6. Обновить страницу и переключить вкладки — соединение должно сохраниться.
7. Повторно нажать подключение при действующем соединении — не должно появиться второго клиента или дублей из-за двух читателей.
8. Отключить питание камеры либо закрыть её соединение; проверить реакцию при обнаружении разрыва. Не обещай мгновенное обнаружение при простом извлечении кабеля: TCP может обнаружить это с задержкой.
9. Вернуть камеру и повторно нажать подключение; повторить чтение кода.
10. Перезапустить программу: настройки восстановлены, журнал пустой, соединение устанавливается после нажатия кнопки.
11. При необходимости выбрать две камеры: первая реальная, вторая с недоступным свободным адресом в моей сети. Проверить, что ошибка второй не мешает первой. Затем вернуть количество камер к одному. Это проверка независимости отказов, а не испытание двух реальных камер.

Также проверь, что изменение настроек без сохранения не переживает перезапуск.
