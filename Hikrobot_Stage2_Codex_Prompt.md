## 3. Сборка сообщений

TCP передаёт поток байтов. Одно чтение не обязательно соответствует одному сообщению.

- У каждой камеры отдельный буфер, относящийся к конкретному соединению.
- Накапливай байты и выделяй сообщения от `{` до `}` включительно.
- Обрабатывай все полные сообщения в одном чтении, сохраняя порядок; незавершённый хвост оставляй до следующих байтов.
- Не жди перевода строки или паузы между чтениями. Не используй длительность паузы как признак конца сообщения.
- После отключения, ошибки связи или переподключения очищай буфер этой камеры. Хвост старого соединения нельзя объединять с новым.
- Корректные сообщения могут идти вплотную: `{...}{NoRead}{...}`.
- Пробелы, CR и LF между сообщениями допустимы и не создают пустые записи.
- Посторонние непустые данные вне скобок отмечай в диагностике; восстанови синхронизацию на следующем `{`.
- Вложенные скобки не входят в протокол. Новый `{` до закрытия текущего сообщения означает повреждённый/оборванный фрагмент: отметь ошибку и начни сбор с нового `{`.
- Ограничь размер отдельного сообщения/незавершённого буфера, например 64 КиБ. При превышении покажи ошибку, отбрось повреждённый фрагмент и восстанови сбор на следующем начале сообщения. Не отбрасывай корректную последовательность множества коротких сообщений только потому, что суммарный объём потока велик.
- При EOF с незавершённым сообщением запиши диагностическое событие и очисти хвост. Это не NoRead.
- Сохрани сырой журнал этапа 1 без изменений смысла: запись сырых данных соответствует чтению TCP. Дополнительные события обработки явно отличаются от сырых чтений.

Рабочий протокол этапа 2 — сообщения в скобках. Старые строки без скобок не угадывай и не разбирай по чтениям TCP. Для несовпадения настроек камеры покажи диагностическую причину.

## 4. Парсер данных

Пример одной записи:

```text
{id:405947004000041,p:(2261,1426),a:2}
```

Пример нескольких записей:

```text
{id:405947004000041,p:(2163,1603),a:2;id:531952002000010,p:(2771,1586),a:1}
```

Разделитель записей — `;`. Для совместимости с шаблоном камеры допускается один завершающий `;` перед `}`. Пустые записи в середине, например `;;`, не являются корректными QR-записями.

Из каждой записи получи:

| Поле | Требование |
|---|---|
| ID | Непустая ASCII-строка до 15 символов. Не преобразовывать в число; ведущие нули сохранять. Не вводить ограничение «только цифры», которого нет в ТЗ. Разделители протокола и пробельные символы внутри ID недопустимы. Слишком длинный ID — ошибка, а не усечение |
| X | Первое число в `p:(X,Y)` |
| Y | Второе число в `p:(X,Y)` |
| A | Число после `a:` |
| SN | Целое 1–4, вычисляется только в Python из A |

X, Y и A могут содержать дробную часть с точкой и знак; обычная числовая экспоненциальная запись также допустима. Все числовые значения должны быть конечными. Нечисловые значения, NaN, Infinity и переполнение — ошибка входных данных. Не подставляй нули при неудачном преобразовании.

Допускай пробелы вокруг полей и числовых значений; не изменяй содержимое ID. Проверяй всю запись, а не только найденный внутри фрагмент регулярного выражения. Отсутствующие поля, повторные поля, лишние данные и неизвестные поля должны давать ошибку формата. Входящий SN не предусмотрен протоколом.

X/Y не меняй местами: несмотря на неточные комментарии в типе SCL, алгоритм `HikrobotParser` берёт X первым, Y вторым. Не вводи масштабирование.

Не ограничивай разбор текущим ожидаемым количеством кодов в настройках. Например, при ожидании 1 сообщение с 2 кодами нужно разобрать полностью: на этапе 3 второй код должен вызвать ошибку количества. Также нельзя молча обрезать входящий список до четырёх записей — это скрывает лишние данные.

### Результат разбора и повреждённые сообщения

Отдели сборку сообщения, парсинг и вычисление стороны от HTTP/UI. Сделай функции/классы, которые можно проверить без реальной камеры.

Для одного полного сообщения возвращай структурированный результат: источник, время обработки полного сообщения, исходное сообщение, вид `codes` / `no_read` / `error`, записи и диагностические ошибки. Для кодов сохраняй порядок записей в сообщении. Между камерами используется фактический порядок обработки полных сообщений на сервере.

Для этапа 2 выбери атомарную обработку сообщения: сначала проверь все записи. Если хотя бы одна повреждена или имеет недопустимый угол, сообщение показывается как ошибочное; его частичный набор не публикуется как корректный и не добавляется в историю корректных кодов. Исходные данные и причина остаются в журнале. Этот подход не должен мешать обработке следующего корректного сообщения. На этапе 3 ошибки будут передаваться в контроль цикла; сейчас цикл не реализуется.

Повторные одинаковые ID не удаляй: в этапе 2 отображаем наблюдения, а объединение уникальных ID относится к этапу 3.

## 5. Расчёт SN и совместимость с Siemens

Сначала проверь исходное числовое A: допустимы **0–360 включительно**. Значение за пределами вызывает ошибку «Угол вне диапазона 0–360». Не нормализуй через остаток от деления, не ограничивай границами и не вычисляй SN для такого результата.

Проверяй диапазон до преобразования к Siemens REAL и до округления. Значения `-0.000001` и `360.000001` должны быть отклонены, даже если последующее преобразование/округление дало бы 0 или 360.

Затем воспроизведи преобразование `REAL_TO_INT` из исходного SCL:

- Siemens REAL — IEEE 754 binary32. Для вычисления стороны учитывай представление A в binary32, затем округление к ближайшему целому.
- На точной половине между целыми применяется округление к чётному, а не всегда вверх.
- Простое `int(A)` не соответствует исходной логике.
- В UI показывай исходный полученный угол A; округлённое значение используй для расчёта стороны. Не выдавай округлённый угол за исходный.
- Выполни binary32-преобразование средствами стандартной библиотеки, например struct; NumPy для этого не нужен.

Таблица для округлённого целого угла:

| Угол | SN | Сторона |
|---|---:|---|
| 0–45 или 316–360 | 3 | Лево |
| 46–135 | 1 | Верх |
| 136–225 | 4 | Право |
| 226–315 | 2 | Низ |

Контрольные значения:

| Исходное A | Целое после округления | SN |
|---:|---:|---:|
| 0 | 0 | 3 |
| 45 | 45 | 3 |
| 45.4 | 45 | 3 |
| 45.5 | 46 | 1 |
| 46 | 46 | 1 |
| 90 | 90 | 1 |
| 135 | 135 | 1 |
| 135.5 | 136 | 4 |
| 136 | 136 | 4 |
| 180 | 180 | 4 |
| 225 | 225 | 4 |
| 225.5 | 226 | 2 |
| 226 | 226 | 2 |
| 270 | 270 | 2 |
| 315 | 315 | 2 |
| 315.5 | 316 | 3 |
| 316 | 316 | 3 |
| 360 | 360 | 3 |

Проверь также половины с чётным нижним целым: 44.5 → 44, 134.5 → 134, 224.5 → 224, 314.5 → 314. Добавь случай рядом с половиной, где binary32 меняет результат относительно прямого round над Python float: 45.4999999 преобразуется в binary32 45.5 и даёт SN 1.

Справочная документация Siemens по округлению: https://cache.industry.siemens.com/dl/files/829/109814829/att_1120874/v1/s71200_system_manual_en-US_en-US.pdf . Главный источник конкретных диапазонов — блок HikrobotParser в приложенном TechVision.scl.

## 6. NoRead

- Полное сообщение `{NoRead}` возвращает результат вида `no_read`, без QR-записей. Допустимы внешние пробелы внутри скобок, но не произвольный регистр или другие слова.
- Не добавляй NoRead в историю QR-кодов, не превращай в ID.
- Не стирай историю при NoRead.
- Не считай NoRead причиной потери TCP-связи.
- Пока не выдавай технологическую ошибку «Код не прочитан»: суммарная обработка по всем выбранным камерам относится к этапу 3.
- `{}`, повреждённое сообщение, EOF и молчание камеры не являются NoRead.

### Главный центральный блок

Пока технологических циклов нет, переименуй заголовок «Текущий цикл» в **«Последнее сообщение»**, а таблицу «Коды текущей детали» в **«Коды последнего сообщения»**. Эти временные названия делают режим этапа 2 понятным. На этапе 3 вернём отображение цикла.

Покажи номер камеры, время и вид последнего обработанного полного сообщения:

- `codes`: «Разобрано кодов: N», таблица всех его записей с ID, SN/стороной и исходным A. Источник — номер камеры. N является количеством записей этого сообщения, не уникальными ID текущей детали.
- `no_read`: «Камера N: NoRead», QR-таблица текущего сообщения пустая. Это информационное состояние, не общая ошибка детали.
- `error`: «Ошибка разбора» и точная причина; QR-таблица текущего сообщения пустая. Последние корректные записи остаются в истории.
- До первого полного сообщения: «Ожидание данных».

Если пришло сообщение другой камеры, центральный блок показывает именно последнее полное сообщение. На этом этапе это не суммарный набор камер и не набор деталей за таймер.

При незавершённом TCP-фрагменте не обновляй таблицу частично. Сырые байты уже видны в журнале.

Таймер и прогресс времени пока не активируй. Покажи короткое пояснение «Сбор и проверка цикла — этап 3». Блок строк ПЛК остаётся пустым с указанием, что обмен ещё не реализован. Не показывай успешный технологический цикл или подтверждённые строки ID;SN.

Если камера-источник последнего результата отключена, пометь показанные данные как ранее полученные; не создавай впечатление нового актуального считывания. При общей кнопке отключения можно оставить последнее сообщение с явной отметкой «Приём остановлен».

### История

- Реализуй FIFO из последних **10 корректно разобранных QR-наблюдений**, общий по всем камерам.
- Столбцы: время, камера, ID, SN/сторона, A, X, Y.
- Одна QR-запись — одна строка; повторы ID также добавляются.
- Внутри сообщения порядок поступления сохраняется; новую историю можно показывать сверху, но порядок должен быть стабильным и документированным.
- NoRead и ошибочные сообщения остаются в журнале, но не добавляются в QR-историю.
- История только в памяти, при запуске пустая. Закрытие страницы и отключение камер её не очищают.
- Переключение вкладок, обновление страницы и опрос API не должны повторно добавлять записи. Парсинг выполняется один раз на сервере при приёме полного сообщения.

### Журнал и настройки

Сохрани сырой журнал и добавь различимые события сборки/разбора/NoRead/ошибок с источником. Не создавай повторные события от опроса браузера. Журнал остаётся ограниченным по размеру.

Все настройки этапа 1 сохраняются. Ожидаемое количество кодов и окно сбора пока не используются в технологической логике.

Исправь горизонтальное переполнение страницы, если оно есть: на присланном пользователем экране правый край центрального блока и подписи обрезаны. Сохрани композицию макета, но обеспечь ширину по доступному окну, min-width:0 для растягиваемых областей и локальную прокрутку только у таблиц, если необходима. Не уменьшай текст до нечитаемого размера.

## 8. Кнопка «Отключить все камеры»

Добавь в левом блоке под кнопкой подключения вторую общую кнопку **«Отключить все камеры»**. Подключение остаётся основной синей кнопкой, отключение — вторичной. Индивидуальные кнопки на каждой карточке не нужны.

- Отключай все соединения, которыми реально управляет менеджер, включая попытки подключения и позиции, исключённые из текущего количества камер.
- Отмени незавершённые подключения и задачи чтения, закрой сокеты, очисти буферы сборки. Заверши операцию только после корректного прекращения задач.
- Не позволяй запоздалому результату подключения снова установить статус «Подключено» после команды отключения. Продумай конкуренцию подключения/отключения и поколение задач.
- После завершения выбранные камеры имеют статус «Отключено», остальные «Не используется».
- Это ручное отключение, а не ошибка сети: журнал «Отключено пользователем», без красного сообщения об аварии из-за отмены задачи.
- Не останавливай FastAPI и не закрывай веб-интерфейс.
- Настройки и история остаются. Входящие данные после завершения отключения не должны публиковаться от старых задач.
- Повторное отключение безопасно. Если нет ни соединений, ни попыток подключения, кнопку можно отключить визуально.
- Во время операции показывай короткое состояние «Отключение…» и предотврати конфликтующие команды. Если идут попытки подключения, пользователь должен иметь возможность остановить их общей кнопкой.
- После отключения кнопка подключения позволяет снова подключиться и читать данные. Сохрани защиту от двух задач чтения на одну камеру.

## 9. Автоматические проверки

Сохрани проходящие тесты этапа 1 и добавь целевые проверки новой логики без реального оборудования:

1. Реальное сообщение с одним кодом; сообщение с двумя кодами; сообщение с четырьмя кодами.
2. Сообщение с ведущими нулями в ID; слишком длинный и пустой ID.
3. Сообщение разделено в каждой возможной позиции байтов — итог одинаковый, сообщение обработано ровно один раз.
4. Несколько сообщений в одном чтении, включая `{NoRead}` между кодами; полный пакет плюс незавершённый хвост.
5. Независимые буферы двух камер при перемежающихся фрагментах. Используй тесты буфера, не создавай приложение-имитатор.
6. Незавершённый хвост очищается при отключении/переподключении; новые данные не склеиваются со старыми.
7. Повреждённое сообщение, вложенная `{`, посторонние байты и превышение лимита: понятная диагностика и восстановление при следующем корректном пакете.
8. NoRead отдельно, `{}` не NoRead, сообщение с завершающим `;`, пустая запись в середине.
9. Все границы таблицы SN, половины, binary32-пример, -1, -0.000001, 360.000001, 361, нечисловые/неконечные значения.
10. При одной повреждённой записи многострочное сообщение не публикуется частично; следующее корректное принимается.
11. FIFO 10, повторные ID сохраняются, NoRead не добавляется, опрос API не повторяет историю.
12. Отключение во время подключения/чтения, повторное отключение, повторное подключение. Нет оставшихся читателей и запоздалого восстановления состояния.

Не меняй проект ради искусственного покрытия. Прогони доступные тесты и проверку запуска. Если нет доступа к моей камере, явно отдели программные проверки от испытания оборудования.

## 10. Инструкция для моего испытания

2. Если зависимости изменились, установить их через существующий `.venv`; новый venv не создавать.
3. Запустить сервер из `D:\OBJECTS\HikRobot`:

```powershell

```

4. Обновить страницу, подключить одну камеру с сохранённым IP и портом.
5. Прочитать один код: центральная таблица должна показать ID, исходный A и вычисленный SN; история — X и Y.
6. Прочитать два разных кода одной камерой: обе записи должны появиться, даже если в настройках ожидается один. На этом этапе ошибки количества ещё нет.
7. Повторить тот же ID: история получает ещё одно наблюдение, уникальность пока не проверяется.
8. Повернуть лист примерно на 90°, 180°, 270° и около 0°: сравнивать SN с фактически пришедшим A, а не с визуальной оценкой положения листа.

Испытание границ дробных углов и повреждённых пакетов выполняется программными тестами, а не требованием вручную заставить камеру выдавать такие значения.
